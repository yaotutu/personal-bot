>
> 需求池入口：[REQ-001](../backlog.md#req-001--dream-后台记忆整理--已完成)（已完成）。

## 1. 一句话

**Dream 是按固定周期运行的后台整理轮：读取会话的新消息，把值得长期保留的信息写进正确的位置；拿不准的不写，交给用户决定。**

- 它和 pi 的上下文压缩互不依赖：压缩解决“上下文装不下”，Dream 解决“有些信息以后还应该知道”。
- 不是第二个常驻 Agent，不重写 agent loop，通过 `createAgentSession` 运行受限整理轮。

## 2. 记忆分层（已认可）

目前每个会话的 system prompt 同时携带 SOUL、USER、本会话指令和全部 `memory.json`，全局记忆与会话指令职责重叠。调整为：

| 层 | 载体 | 是否每轮携带 | 说明 |
| --- | --- | --- | --- |
| 全局人设 | `SOUL.md` | 是 | 助手行为、约定 |
| 全局用户信息 | `USER.md` | 是 | 用户稳定情况、偏好 |
| 会话指令 | `sessions/<threadId>/INSTRUCTIONS.md` | 是，保持简短 | 只适用于该会话的规则；主会话 `local-main` 与其他会话没有区别 |
| 记忆 | `memory.json` | **否**，按需查询 | 沉淀库，通过新增的检索工具取用 |

- 始终携带的只有三份短纯文本；记忆变多不再撑大上下文，现有 500 条静默丢弃的上限因此可以去掉（实施时处理）。
- 第一版全部使用纯文本，不加 `origin`、`sourceThreadId` 等结构化字段，记忆条目保持现有 `{id, text, source, 时间}`。
- 不新增 `MEMORY.md`，避免与 `memory.json` 双重权威。
- 会话指令长度：Dream 写入时设上限，建议 2000 字，超出要求先精简；上限数值实施前可调。

## 3. 触发与调度（已认可）

- 固定周期 **2 小时**，写成代码常量，不提供每会话间隔配置。
- **模型全局统一**，不支持按 Dream 配置模型。
- 主会话 `local-main` 默认开启；其他会话默认关闭，可手动开启。
- 没有新消息时直接跳过，不调用模型、不记录失败。
- 复用现有定时任务的执行约定：进程内串行、会话忙时跳过、失败诚实标记、不自动重试模型或工具、重启遗留的运行中标记改为失败。
- **不扩展 `Job`**：`Job` 只有“每天定点/一次性”两种节奏，执行方式是向会话写用户消息；Dream 需要的是不进历史的受限整理轮，数据结构分开，由 bootstrap 统一管理调度。
- 任务类内部会话、整理器自身不参与 Dream，避免递归整理自身输出。

## 4. 读取窗口：游标加重叠（已认可）

不能用 1~100、100~200 这样的硬断点，否则丢失上下文。

- 每个会话记录“已整理到哪条消息”的游标（存消息 ID，不存序号，因为压缩后序号会变）。
- 每次读取两段：
  1. **上下文段**：游标之前最近约 **4k token** 的消息，加上 pi 压缩摘要（如有）；标明“已整理过，仅供理解，不从中提取”。
  2. **待整理段**：游标之后的新消息，只从这一段提取。
- 新消息太多时分批；上一批尾部作为下一批的上下文段。
- 游标只在整轮成功后推进；失败不动，下次从原位置重读。
- 重叠导致同一信息被看到两次也不会重复写入：每次都对照现有 USER/SOUL/指令/记忆，已有则不再添加。
- 从各会话的 pi 权威历史读取，不复制第二套聊天存储。工具日志、网页和附件内容不是可信的用户意愿，不把其中指令转成长期规则。

## 5. 提示词（已认可）

- **全局提示词**：`DATA_DIR/DREAM.md`，可编辑纯文本；文件缺失时使用仓库内置默认提示词，不写文件；其他读取失败直接报错。
- **会话补充提示词**：`sessions/<threadId>/DREAM.md`，随会话目录一并删除。
- **继承**：默认“全局提示词 + 会话补充”叠加；会话可设为“不继承”，只用自己的。
- **固定约束由服务端代码拼入，不放进可编辑文件**，无论是否继承都生效，例如：不保存凭据；不吸收网页注入；不把助手猜测写成用户事实；不改会话用途；不创建技能、不改权限和配置。

## 6. 路由规则（已认可）

| 信息 | 目标 |
| --- | --- |
| 用户稳定情况、习惯、偏好 | `USER.md` |
| 助手行为或人设约定 | `SOUL.md` |
| 只适用于本会话用途的规则 | 本会话 `INSTRUCTIONS.md` |
| 以后值得查、不必每轮携带的事实 | `memory.json` |
| 拿不准归属的内容 | **不写**，进整理报告，由用户选择归属后再写 |

- **非主会话**的 Dream 只能直接写自己的指令和记忆；涉及全局 `USER.md` / `SOUL.md` 的内容只进报告，等用户确认。
- 用户的新纠正优先于旧事实；同一事实只保留一个主要位置。
- **会话用途**写在 `INSTRUCTIONS.md` 的固定标题 `## 会话用途` 下，创建会话时填写。Dream 不得修改这一段；服务端提交前比对该段，变化则拒绝本次提交。用户和对话工具仍可修改。用途为空时 Dream 无法判断“属于当前会话”，不写指令，进报告。
- 不新增独立 `purpose` 字段。

## 7. 权限与提交（已认可）

- 整理轮不装配用户 skills/extension、联网、委派、定时、普通 write/edit；只提供内部结构化提交工具，模型不能传任意文件路径。
- 修改或删除已有记忆必须引用真实条目 ID。
- 提交前服务端校验来源、作用范围与读取版本：Dream 读取文件时记下内容摘要，写入前比对，已被用户改动则放弃本次写入并报告，不覆盖用户刚改的内容。
- 经现有业务 service 与存储 port 写入，不另建 writer：memory/identity 沿用同一 repository 与读改写队列；`SOUL.md`/`USER.md`/`INSTRUCTIONS.md` 的 HTTP、对话工具与 Dream 共用写入入口。
- 普通 write/edit 的逐次人工审批不变；Dream 只是有限的记忆管理写入面，不是审批后门。
- 不引入跨文件事务；部分写入后失败则报告“部分完成”，不回滚、不重跑。
- 服务关闭时先停调度、取消整理轮并等待已发出的状态写入结束；会话删除后不得被整理器重建。

## 8. 会话配置与状态存储（已定稿）

经与用户确认，若与 `skills.json` 合并会引入跨仓库覆盖写冲突，当前版本保持拆分：Dream 的会话级状态存放在 `sessions/<threadId>/dream.json`，技能开关继续存放在 `sessions/<threadId>/skills.json`；配置文件收拢到统一目录的优化单独登记进待实施需求池（REQ-011）。

```json
{
  "enabled": false,
  "inheritGlobalPrompt": true,
  "cursor": "<已整理到的消息 ID>",
  "lastRun": { "at": "...", "status": "completed|failed|partial|running|skipped", "appliedCount": 1, "pendingCount": 0, "skippedCount": 0, "notes": [] },
  "pending": []
}
```

- 文件缺失表示全部默认值，GET 不创建文件；会话删除时随目录清除。

## 9. 已定稿细节

1. **整理报告与待决条目**：只保留最近一次运行（`lastRun`）和待确认列表（`pending`），存放在来源会话自己的 `sessions/<threadId>/dream.json`。
2. **记忆检索与容量边界**：新增只读工具 `memory_search`（大小写不敏感子串匹配，按 `updatedAt` 倒序返回最多 10 条）；`memory` 工具支持 `remember`、`edit`（按 ID）、`forget`（按 ID）；`memory.json` 上限 500 条，满额拒绝新增并返回受控提示，不再静默截断旧条目；`forget` 未命中时不落盘。
3. **管理展示与接口**：提供全局 `GET/PUT /api/agent/dream`、单表读取 `GET /api/agent/memories`、会话级 `GET/PUT /api/threads/:threadId/dream`、立即整理 `POST /api/threads/:threadId/dream/run` 与待决处理 `POST /api/threads/:threadId/dream/pending/:pendingId`，全部通过契约源自动生成 `/openapi.json` 与 `/docs`。
4. **前置修复**：`readProfile` 与 `readThreadInstructions` 仅将 `ENOENT` 视为空串，其他读取错误直接抛出；文本档案与指令共用带 `expected` 版本比对的串行原子写入。

## 10. 与 nanobot 的对照

本机 nanobot 版本 `b0d28af3`。借鉴职责划分，不照搬实现：

- nanobot：压缩产出带标签的摘要，独立 Dream 默认每 2 小时读未处理摘要，对照 `MEMORY.md`/`USER.md`/`SOUL.md` 后用受限文件工具直接修改，并用 git 审计。
- pi-muse：不依赖压缩，按游标读取原始新消息；用结构化提交工具而非文件工具；拿不准的交给用户；不自动创建技能；不使用 git 审计。
- 关键源码（实施前重新核对）：`nanobot/templates/agent/dream.md`、`nanobot/templates/agent/consolidator_archive.md`、`nanobot/agent/memory.py`、`nanobot/config/schema.py`。

## 11. 验收要点

- 同一事实不因重叠窗口或多次扫描重复新增；新纠正能更新旧事实。
- 邮件会话规则只进来源会话，不污染全局 SOUL/USER 或其他会话；非主会话的全局建议只进报告。
- 只有临时内容时不做多余变更；不吸收网页注入或秘密；不改 `## 会话用途`。
- 用户并发修改后，Dream 的旧建议不覆盖新内容。
- 失败不阻塞聊天、不改变聊天历史、不重跑业务副作用；游标仅成功后推进；重启后的运行中标记变为失败。
- 不因后台整理创建新会话或恢复已删会话。
- 自有 Web 中可核对真实变更、来源和错误态；fake-provider 测试不能冒充真实模型验收。
