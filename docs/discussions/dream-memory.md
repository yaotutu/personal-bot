# Dream 后台记忆整理

> 记录日期：2026-10-18。
>
> **状态：用户已认可方案，暂缓实施。**用户明确要求先记录，晚点与其他需求一起做；本文件不授权立即编码、启动整理任务或修改真实记忆。
>
> 需求池入口：[REQ-001](../backlog.md#req-001--dream-后台记忆整理)。

## 1. 一句话

**pi 继续负责正常的上下文压缩；新增 Dream 后台任务，把值得长期保留的信息维护进现有记忆和规则。**

- 压缩解决“这段聊天太长，模型装不下”。
- Dream 解决“这段聊天里有些事实、偏好或规则，以后还应该知道”。
- 它是服务内部的一项后台业务能力，不是第二个常驻 Agent，也不为它重写 agent loop。

## 2. 已确认的产品方向

1. 用户接受摘要式压缩可能丢失细节；压缩不是无损长期记忆系统。
2. 在压缩关联的整理过程中，自动提取有长期价值的信息并持久化是合理的，不再将“必须由用户逐条说记住”作为未来功能的唯一入口。
3. 复用 pi 的上下文压缩与权威历史，不自行实现第二套压缩算法或聊天历史。
4. Dream 对照现有记忆执行新增、合并、纠错或删除过时信息，不是每轮无差别追加。
5. 全局事实和来源会话的专属规则必须分开，不能将邮件会话规则提升成全局规则。
6. 后台运行，不阻塞正常聊天；失败不破坏已有历史，不自动重跑已经发生副作用的业务操作。
7. 用户可看见整理结果，并能通过已有管理能力纠正或删除错误记忆。

## 3. nanobot 源码参考

本轮核对的本机 nanobot 版本为 `b0d28af3`。以下描述仅对应该版本，不代表所有历史版本。

- 压缩先生成当前会话的 summary checkpoint，并可将提炼内容追加到 `memory/history.jsonl`。
- 其压缩提示词会保留工作交接信息，并用 `permanent`、`durable`、`ephemeral`、`correction` 标记候选事实；不是单纯机械缩短文本。
- 独立 Dream 定期读取未处理的历史摘要，对照已有记忆，使用受限文件工具更新 SOUL、USER、MEMORY 或用户技能；默认周期为 2 小时。
- Dream 正常完成才推进已处理位置；文件修改是实际工具副作用，后续失败不自动回滚。

关键源码位置（未来实施前重新核对）：

- `nanobot/templates/agent/consolidator_archive.md`：压缩摘要的筛选和分类规则。
- `nanobot/templates/agent/dream.md`：长期记忆归类、去重、纠错、清理要求。
- `nanobot/agent/memory.py`：压缩归档、Dream 输入批次和受限工具。
- `nanobot/cli/gateway_runtime.py`：Dream 内部定时任务执行与结果确认。
- `nanobot/config/schema.py`：Dream 配置。

**借鉴职责划分，不照搬其 history.jsonl、任意文件编辑方式、技能自动生成或 Git 审计机制。**pi-muse 已有自己的存储、权限和执行边界。

## 4. 第一版实施基线

以下是本轮认可方案的具体基线，尚未落地；文件名、接口名和字段在实施前核对当前代码后确定，不把示例当作已发布契约。

### 4.1 触发与执行

```text
用户正常聊天
    ↓
pi 自动压缩成功，权威历史中出现新压缩记录
    ↓
后台周期性查找尚未整理的压缩内容
    ↓
读取来源会话的摘要、必要原文和已有记忆/规则
    ↓
通过受限的 pi 整理轮提出结构化修改建议
    ↓
服务端校验来源、作用范围、目标版本后提交
    ↓
记录实际结果，后续正常对话重新加载
```

- 推荐默认每 2 小时检查一次，进程内串行，不让每次压缩都阻塞用户对话。
- 第一版只处理已发生压缩的内容；没有压缩的近期对话仍可通过显式记忆工具保存，不承诺立即自动沉淀。
- 保留“自动整理开关”和“立即整理”管理入口。
- 排除整理器自身和内部后台任务会话，避免递归整理自身输出。来源会话关闭记忆能力时，不继续从该会话自动沉淀。
- 调度由 bootstrap 统一管理，HTTP 不创建另一份服务或启动另一套 scheduler。

### 4.2 输入

- 从各 thread 的 pi 权威历史读取压缩记录及其来源，不复制一套聊天存储。
- 压缩摘要用于工作背景；对应原始用户/助手对话用于核对事实、纠正和作用范围。
- 工具日志、网页和附件内容不是可信的用户意愿；必要引用须保留来源属性，不把其中的指令转成长期规则。
- 对照当前 `memory.json`、`SOUL.md`、`USER.md` 及来源会话的 `INSTRUCTIONS.md`。
- 批次有大小限制；超限则拆分，不静默截断后标记整批完成。

### 4.3 输出与归属

| 信息 | 目标 |
| --- | --- |
| 用户稳定情况、习惯、偏好 | `USER.md` |
| 用户确认的全局助手行为约定 | `SOUL.md` |
| 长期事实、项目知识和持续有效决策 | 现有 `memory.json` |
| 只适用于来源会话的规则 | `sessions/<threadId>/INSTRUCTIONS.md` |
| 一次性调试、重复错误、临时状态 | 通常不进入长期记忆；工作摘要或工作文件承载 |

- **不新增 `MEMORY.md`**，避免与现有 `memory.json` 双重权威。
- 同一事实优先保留一个主要位置；已存在则合并或修正，不反复追加。
- 用户的新纠正优先于旧事实；不把助手猜测写成用户事实，不保存凭据等秘密。
- 不自动扫描或修改其他会话的私有工作文件，不把“可以整理会话规则”扩大成全盘访问权限。
- 自动创建技能、修改工具权限、调整模型/配置不在第一版范围。

### 4.4 权限与提交

- 整理轮使用现有配置的模型，通过 `createAgentSession` 运行，不手写 agent loop。
- 不装配用户 skills/extension、联网、委派、定时、普通 write/edit 等能力。
- 仅提供内部的结构化建议提交工具（名称待定，例如 `propose_memory_changes`）；模型不能传任意文件路径。
- 每项建议带目标、操作和来源消息；修改/删除已有记忆须引用真实条目 ID。
- 正常结束且建议校验通过后，服务端经业务 service 和存储 port 保存；不让模型用通用文件工具直接改系统数据。
- memory/identity 使用原来同一份 repository 和完整读改写队列，不另建 writer。
- SOUL/USER/INSTRUCTIONS 的 HTTP、对话工具和 Dream 共用写入入口；提交时检查读取版本，冲突则跳过并报告，不能覆盖用户刚改的内容。
- 普通 write/edit 的逐次人工审批边界不变；Dream 是单独授权的有限记忆管理写入面，不是文件工具审批后门。

### 4.5 进度、失败和生命周期

- 可新增 `memory-consolidation.json`，仅存来源 thread/pi-session/compaction ID、批次状态、时间、实际变更目标及受控错误；最终名字和 schema 尚未发布。
- 不在该文件另存完整历史或摘要；历史仍由 pi 唯一管理。
- 同一来源批次不在每次扫描重复执行；失败显式记录，用户可主动再次整理，不自动重试模型或工具。
- 重启遗留 running 标记 failed，不做 durable execution 或断点续跑。
- 不引入跨文件事务；部分目标已写、后续失败时报告“部分完成”，不假称全部成功，不自动回滚或重跑。
- 服务关闭时先停调度、取消整理轮并等待已经发出的状态写入结束；不得遗留后台执行。
- 来源会话删除时不得被整理器重建；规则提交前重新确认来源仍存在，相关待处理内容按删除边界跳过。

### 4.6 管理展示

最小展示：自动整理开关、立即整理、最近执行时间、成功/失败/部分完成、实际新增/修改/删除内容与来源会话。所有新端点按现有 zod schema 和 endpoints 注册表生成文档，不手写 OpenAPI。

## 5. 建议实施顺序与验收

1. **统一提交入口**：记忆批量修改；SOUL/USER/会话规则共用 writer、版本校验和安全路径。
2. **后台整理链路**：pi 摘要/来源适配、受限整理轮、周期调度、进度记录与生命周期。
3. **管理与真实验收**：开关、手动触发、结果展示和真实模型场景。

关键验收：

- 同一事实不因多次扫描重复新增，新纠正能更新旧事实。
- 邮件规则只进来源会话，不污染全局 SOUL/USER 或其他会话。
- 只有临时内容时不做多余变更；不吸收网页注入或秘密。
- 用户并发修改后的新版本不被后台旧建议覆盖。
- memory 上限、坏数据读取、部分失败和重启状态均诚实处理。
- 整理失败不阻塞聊天、不改变聊天历史、不重跑业务副作用。
- 不因后台整理创建新的公开用户会话或恢复已删会话。
- 自有 Web 中可核对真实变更、来源和错误态；fake-provider 测试不能冒充真实模型验收。

## 6. 与当前实现的关系

当前项目文档中的“记忆只显式写入、不自动提取”描述的是**现有实现**。Dream 是用户于 2026-10-18 认可的后续扩展，不应在仅记录需求时提前把现有行为文档改成“已支持自动整理”。

正式开工时须一起更新 AGENTS.md、README、架构与配置说明中相关约定，并明确新增记忆管理权限；在此之前不启动 Dream、不修改模型或文件工具权限。

坏上下文的“强制新开对话但保留规则/记忆/工作区”是另一项需求（见需求池 REQ-002），不混入本次压缩与记忆整理的实施范围。
