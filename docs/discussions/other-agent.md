# other agent（常驻专职 agent）讨论记录

> 状态：**设计讨论中，未实现，先记录不写码**。记录于 2026-10-16 的讨论。本文件只在思路
> 被确认或改动时更新，不是承诺，也不代表已实现。后续启动时按"一次只攻一块"推进。
> 分块标记：`decided=已确定` / `open=未确定，专注聊这些` / `ready=可开发`。

## 一、概念澄清（decided）

- **subagent ≠ other agent**，两者是不同东西：
  - **subagent**：主 agent 派的一次性临时工，没有持久上下文，一个提示词去干、干完消失。
  - **other agent**：**常驻的专职主角，能力与主 agent 完全一致**（同一 pi 引擎、同一模型、
    全套工具），只是绑定一个**固定职责方向**（如"邮件 agent"只管邮件）。它不是临时任务，
    是长期存在的对面。用户比喻：**主 agent 是全能型选手，other agent 是有固定方向的专职选手**。
- 其他 agent 之间**不通信**；每个 other agent 独立。

## 二、产品行为（decided）

1. 主 agent 是全能型，可在其窗口聊任意内容。
2. 主 agent 可**丢任务给 other agent**（如"发个邮件"）——唤醒 other agent 干活；
   **主 agent 不关心细节，只关心结果**。
3. 用户也能**切换到 other agent 的独立窗口，跟它私聊**。
4. **会话隔离是双向的**：主窗口只见"唤醒某 other agent → 结果"，不见 other agent 的完整
   对话过程；other agent 窗口只见自己的完整对话，不见主 agent 的聊天。
5. 两者**共享同一份数据/文件世界**（共享工作目录与数据），但**会话内容互不出现**。

## 三、工作区模型（decided）

- **每个 agent（主 agent + 每个 other agent）各有一块自己独立的物理工作区**（独立目录），
  用于隔离：写草稿、跑命令，别人看不到。这是"防混乱"的关键，用结构隔离而非审批。
- **另有一块全局共享工作区**：当需要交换东西时，把产物放到共享工作区，让目标 agent 读。
  **共享工作区是唯一的交换通道**。
- **不搞不同 agent 之间直接通信**（不建频道、不互发消息）——用户刻意拒绝，因为直接通信
  会把系统变得混乱。用"共享工作区放文件 → 对方读"替代直接通信。
- **系统目录**（config.json / sessions/ / memory.json 等）彻底隔离，任何工具不许碰。

## 四、通信机制（交接靠共享工作区放文件）

> 本节分"已确定"与"待定"：已确定的是"用什么机制"（文件交接，不实时通信），
> 待定的是具体细则。

### decided
- 交接方式 = **文件交接**：A 把东西写进共享工作区 → B 读。
- 不实时通信、不建频道；通信收敛成"放文件 → 对方读"一件事。

### open（未定，专注聊这些）
- **通知**：A 放完文件后，B"怎么知道有消息"？倾向 **B 轮询扫收件箱**（不主动推送）。
- **消息约束/格式**：文件名与内容如何约定（状态名 `.pending`/`.done`？目录 `inbox/<target>`？
  头部 `[from][to][status]`？）。
- **读完后的回执**：B 读完后"怎么标记已处理"（改名 `.done`？）。
- **不重读不漏读**：如何保证一个文件不被两个 agent 都读（防重复/漏读）。

## 五、与 subagent（现有 delegate_task）的关系（decided 判断）

- 项目现有 `delegate_task` + `task-<id>` 后台任务，本质就是"subagent"：派活→独立 thread 跑
  →回结果→（干完即止）。它**没有身份**，用的是与主 agent 相同的 system prompt 和全套工具。
- other agent 与它的差别：**有固定身份**（name + 专属 prompt + 限定 tools），**常驻可私聊**，
  **会话与主 agent 双向隔离**。

## 六、落地方向（decided 判断，未实现）

用户已有大部分零件：
- **多 thread**（每个 thread 独立 pi 会话与历史）→ 独立窗口的基础已有。
- **delegate_task**（派活→跑→回结果）→ 主 agent 呼起 other agent、收结果的形状已有。
- **独立工作区**：按上节工作区模型，把每 agent 的工作区划成独立目录。

缺的核心是一块：**"带身份的 thread"**——把一个后台会话从"无身份的普通任务"升级成
**带固定 name/prompt/tools 的专职单位**，并能独立窗口私聊 + 会话双向隔离。

推进方式：**不推倒重来，是有界的一次改动**；按"一次只攻一块"推进。

## 七、待定点（open）

- other agent 身份定义的位置与结构（名字 / 职责 prompt / 工具集 / 记忆）。
- other agent 的 tools 范围：像"邮件 agent"能否直接发实际邮件（需真实凭据 / 服务），
  还是先只做草稿/计划、由用户手动发。此项用户尚未拍板，属后议。
- 是否复用现有 /api/agent 或新独立 thread 承载 other agent 窗口与私聊。
- 第四节通信机制下的细则（通知 / 格式 / 回执 / 不重读）。

## 八、关联话题（一并挂着，未实现）

- **workspace 拆分**：现在 `workspace/` 同时是"读资料区 + 写盘台 + pi cwd"。建议把
  **读的地盘**（宽）与**写/执行的地盘**（窄）分开定义。见 `docs/architecture.md` 当前边界。
- **bash 开放**：pi-coding-agent **自带** bash 工具，项目未装配且写为"永不暴露"硬边界。
  技术上随时可开，缺的是安全规则（建议沿用 read/write 的**目录白名单**思路：普通命令放行、
  逃逸 workspace 的写操作才拦）。因 workspace 定义未定，暂缓。
