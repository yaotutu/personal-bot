# 审批接口：业务规则讨论

记录日期：2026-10-18。

**状态：业务规则已定稿，用户要求整理后晚点实施，本次不授权接口重构开工。** 审批决定、执行结果、历史列表、单项详情和长期留存按下文执行。本文是实施前业务基线，不是已经提供的接口契约。

本轮统一范围见[工作区接口已确认方案与暂缓清单](workspace-api-design.md)。分页游标、字段、幂等与状态冲突等技术细节由实施方按既有安全边界具体化，不再作为必须让用户逐项选择的问题。

## 已确认的规则

- 当前待审批内容通过全局 SSE 直接推送，包含用户作决定所需的完整预览；批准或拒绝仍通过独立 HTTP 接口提交，SSE 不承载用户操作。
- **批准只代表授权**：允许执行预览中绑定的这一次操作，不代表工具执行成功，也不代表整项 activity 完成。
- **拒绝代表不执行这次操作**：Agent 收到拒绝结果后决定后续如何处理，不直接把整条 activity 自动标为失败。
- **实际结果以真实工具执行为准**：批准后仍可能提交失败；执行成功、失败或取消如实更新对应步骤和进展，不能根据审批状态伪造结果。
- 保留既有安全约束：逐次授权、完整修改预览、文件版本绑定，以及过期、运行取消或文件变化时不得提交该次修改；Agent 不能代替用户批准。

例如：请求保存报告 → 用户批准 → 实际文件提交成功 → 保存步骤完成。若提交失败，记录失败，不把“已批准”显示为“已保存”。

## 已确认：审批历史列表

- 用途是查看以前有哪些操作需要审批，以及当时如何处理；候选接口为 `GET /api/approvals`。
- 列表仅包含已处理或失效的审批：已批准、已拒绝、已过期、已取消。当前待审批项通过 SSE 同步，不混入历史列表。
- 每条返回摘要：操作名称、审批状态、申请和处理时间、所属会话，以及关联的 activity（如果有）。普通对话也可能产生审批，不要求必须存在 activity。
- 分页读取，从最近记录向前翻；不在历史列表返回整份修改预览。查看完整内容使用单项详情接口，具体协议另议。
- 历史中的“已批准”仍只表示同意，不代表操作已经执行成功；不把审批决定和执行结果合成一个状态。

## 已确认：单项审批详情

- 用途是重新查看某次申请的完整内容、用户决定与真实执行结果；候选接口为 `GET /api/approvals/:id`。
- 返回操作信息、目标文件或对象、当时申请审批的完整预览、审批状态与申请/处理时间、来源会话，以及关联的 activity（如果有）。历史预览不能用当前文件内容替代。
- 审批决定与实际执行结果分开。只有存在真实执行结果才返回；没有结果时不猜测成功，也不因已批准就显示“已保存”。例如“已批准，但保存失败，文件版本已变化”应如实表达。
- 当前待审批项已通过 SSE 给出完整预览，不要求再次查询详情才能作决定；详情是重新查看或历史查询入口。
- 读取详情是只读行为，不重新执行操作，不使已处理、过期或取消的授权重新生效。

## 已确认：历史与完整预览长期保留

- 用户明确选择长期保留审批历史和当时的完整修改预览，暂不增加按时间自动清理的逻辑。
- 分页仅控制每次读取数量，不代表只保存最近若干天或最近若干条；不能通过数量上限静默丢弃旧审批。
- 本次确认的是历史数据留存，不是授权无限期有效。保留既有待审批有效期、文件版本绑定及运行取消保护；失效的授权不能因记录长期存在而再次执行。

## 实施时确定的协议细节

- 接口职责对应 `POST /api/approvals/:id/decision`、`GET /api/approvals`、`GET /api/approvals/:id`；这些命名作为后续设计基线，当前尚未替换现有接口。
- 实施方明确请求/响应字段、重复决定与状态冲突、历史分页/排序游标、执行结果缺失或未知的编码。不能因重放决定而再次执行，也不能把未知执行结果填成成功；具体协议与测试一起交付。
- 本次未批准新增产品交互、历史清理或删除接口；长期留存不能被时间/条数裁剪替代。
- activity 的完成仍按[已确认的整项工作完成标准](activity.md#已确认什么时候完成)判断，不从单次审批结果直接推断。

实施时同步修改契约源、自动生成的 `/docs` / `/openapi.json` 及测试，不能用本文代替对外契约。
